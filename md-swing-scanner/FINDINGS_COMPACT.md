### Research Integrity Rules (quoted near-verbatim — standing governance, not narrative)

- **Rule #1 — One Source of Truth** (RQ-47, 2026-09-16/17): no duplicate gate logic, no duplicate candidate definitions — same discipline already used for `detect_entry`/`check_exit`, extended to the priming/classification layer.
- **Rule #2** (2026-09-17, critic-proposed): every feature used for Primed-Gate or live IOC research must be computed from information available *before* the breach. A feature using the breach day's own close/RSI/momentum/volume belongs to Entry-Gate or Audit-Gate research only, never Primed Gate.
- **Rule #3 — Promotion Rule, revised** (2026-09-17): a production gate must (1) improve the Primed population, (2) not materially degrade the Entry population, AND (3) have enough live-representative support (real intraday+13:00-cutoff population) that the effect is observable where it will actually be traded — sample cannot *disappear*, even if not statistically significant.
- **Rule #4 — used for two distinct statements in the source log (preserved as written):**
  (a) *Minimum Population Rule* (2026-09-17): never promote a production rule solely because it improves a population smaller than 500 trades, unless it also improves a larger parent population, or it has an independently-justified mechanism and is being transferred from elsewhere (e.g. VCP geometry transferred from BC).
  (b) *Candidate vs Executable Portfolio* (2026-09-18, at EMA34=2's promotion): a candidate-level improvement is insufficient for production promotion when a feature materially changes candidate volume/selection — its effect on *executable* opportunities must also be established, not just the candidate population's own stats.
- **Rule #6** (2026-09-18): a new result that contradicts an already-established, validated finding must be treated as a bug signal to investigate first, not a "new tension" to report. If a "confirming" second check validates a surprising result, verify the two checks are actually independent (different code path/data slice) — structurally similar computations can share the same bug, and agreement between them is not confirmation.
- **Measurement-anchor sibling rule** (2026-09-19, unnumbered, "sibling to Rule #6"): any test of whether a breach-time feature predicts future price action must anchor forward returns to the breach day's own Close, not the trigger price, whenever the feature could correlate with the Close-vs-trigger gap itself. Trigger-anchored PnL remains correct for reporting realized outcomes of already-decided trades/populations.
- **Standing methodology lessons (non-numbered, still binding):** verify a reused/re-implemented formula against the actual production source, not memory or a "close enough" column (2026-09-13, RVOL baseline bug). A test's population shouldn't inherit a scope restriction from an unrelated earlier test just because that data was on hand — check whether the real data dependency exists first (2026-09-14). Measurement correctness ≠ decision usefulness — a signal measured correctly is necessary, not sufficient, before it can drive a live action (RQ-37 closeout, 2026-09-13). A shared helper function can be correct for the purpose it was built for and silently wrong for a superficially similar new question — check its exact convention before reusing it (2026-09-14, DTE/theta bug). Before trusting a research rerun, verify in this order: (1) population, (2) entry convention, (3) exit implementation, (4) production parameters, (5) only then metric implementation (2026-09-17, Family C process error). concentration must be checked at consistent bucket sizes — a metric that changes when you merely re-slice the same population is lying, not the trades (RQ-48).

## Standing methodology caveat, retroactive (2026-09-20 note attached, applies to 2026-09-06 work)

`portfolio.py`/`simulate_lots()` sorts by `entry_date` and admits purely on cash-affordability — no ranking mechanism, assumes perfect awareness/execution of every affordable candidate the instant it appears (no missed signals, no execution failure). Independently rediscovered building RQ-57 (2026-09-18) — RQ-57 abandoned `portfolio.py` entirely in favor of the real intraday cache + live 9:20 ranking, but that fix was never generalized into a standing rule at the time, so **every capital-constrained CAGR conclusion from 2026-09-06 (fixed-N-day rejection, reactive-3-day-stall re-check below) rests on this unrealistic assumption and should be treated as provisional, not decisive.** Sharper related point: even a "realistic" Top-5-ranking simulation still assumes perfect allocation to the ranked-good trade every time — no simulation eliminates the trader's own real-time execution/luck risk. **This is the actual theoretical justification for asymmetric risk:reward (e.g. 1:3 R) as a design philosophy independent of backtest CAGR**: size wins big enough relative to losses that the system stays profitable under realistic execution variance, rather than trying to guarantee catching the "right" trade every time. Worth deciding explicitly whether a rule is being judged on raw CAGR (vulnerable to this) or distributional robustness (win/loss size ratio, tail risk) — different criteria, can disagree. ## RQ-66: searching for a breach-time predictor of the Unique/Immediate-Fade tail — daily-bar Stage 1 exhausted, a real measurement-artifact caught along the way (2026-09-19)

Since Early/Unique isn't separable live and day+1/2 price action was already ruled out, next question (RQ-66, refined into RQ-66A "Immediate Fade"/RQ-66B "immediate weakness"): can any feature knowable AT BREACH TIME predict a fade before day+1 info exists? Target label: **Immediate Fade** = `close_d1<0 AND close_d2<close_d1 AND close_d3<close_d2` (sharper than the 15-day maturity label).

**A real measurement-artifact caught before reporting (Rule #6 in action)**: `simulate_swing()`/`simulate_day1()` measure pnl relative to `trigger_price` (correct convention for dollar-PnL reporting of already-decided trades — remains valid and unaffected for everything reported earlier in this file). The issue is narrower, specific to FEATURE-PREDICTS-OUTCOME tests: three candidate features (`vol_zscore`, `body_atr_daily`, `dist_to_trigger_pct`) showed dramatic clean-looking separation bucketed by trigger-anchored outcome — **completely vanished when re-anchored to the breach day's own Close** (e.g. `dist_to_trigger_pct`'s day+3 return was flat +0.01-0.13% in every bucket vs an apparent −1.31%→+4.75% swing-exp spread under trigger-anchoring). **Root cause**: `dist_to_trigger_pct` is DEFINED as `(Close/trigger−1)`, so trigger-anchored forward returns carry that exact gap as a built-in constant offset every subsequent day — any feature correlated with the Close-vs-trigger gap inherits a fake predictive signal by construction.

**New standing rule (sibling to Rule #6, "Measurement Anchor Rule")**: any test of whether a breach-time feature predicts future price action must anchor forward returns to the breach day's own Close, not trigger — trigger-anchored pnl stays correct for reporting realized outcomes of already-decided trades/populations (none of which are defined by the Close-vs-trigger gap).
